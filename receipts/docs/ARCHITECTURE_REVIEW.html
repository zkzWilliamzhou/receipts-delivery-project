Architecture review: deepen the Backend seam

Scope before scan: the hot spot is sandbox.py, touched by the safety rounds. Three candidates were surfaced. One was deepened. The golden contract stayed byte-identical.

Vocabulary from GLOSSARY.md and codebase-design: module, interface, depth, seam, adapter, leverage, locality. ADR-0001 and ADR-0002 were read first; no candidate contradicts them.

1. Where the friction was

Before the pass, sandbox.py exposed detect() and wrap() over a bare string. The string was a shallow interface: callers had to know what each name meant. Policy.evaluate asked is_enforcing(name), Engine.run built an attempts list from the name, and ClaimVerifier asked is_enforcing(name) again. Backend knowledge leaked across three seams. Applying the deletion test: deleting the module would not concentrate complexity, it would just move the same name checks into three callers.

2. Candidates

Top recommendation Strong

Candidate A — Deepen sandbox.py into the Backend module

Files. receipts/sandbox.py, receipts/policy.py, receipts/engine.py, receipts/claims.py, tests/test_backend.py.

Problem. A backend name is not a deep interface. Network isolation and filesystem containment were separate facts that no single module owned. Adding a capability meant editing four files, and the real bug hid in how callers interpreted the name, not inside a pure function.

Solution. Backend becomes a value object with one deep interface: Backend.resolve(), Backend.wrap(argv, workspace), Backend.capabilities(), network_isolation, filesystem_containment. Module-level functions stay as thin adapters. Policy, Engine and ClaimVerifier now deal with one object instead of a string plus scattered predicates.

Benefits. Locality improves: the capability decision sits next to the command wrapping that creates it. Leverage improves: one interface now serves detection, wrapping, receipt disclosure, and strict verification. The deletion test flips: removing Backend would concentrate four scattered decisions into one missing module, which is the signal of a deep module. Tests exercise the built argv and the capability matrix through the public interface, not through mocks of the wrapper.

Candidate B — Fold output capture into a Capture adapter

Files. engine.py _popen_run, _read_capped, redact.py.

Problem. Streaming capture and redaction are pure helpers extracted away from the call site. Locality is weak: a future change to the output cap has to be understood in three places.

Solution. A Capture adapter would own subprocess streaming, hashing, truncation and redaction, and return one execution record.

Benefits. Higher leverage for the Engine.run caller. Why not now. A second adapter would not yet be real: the deletion test says the complexity would move, not concentrate. Revisit when replay and run both need a second capture policy. Rejected in this pass to keep the change set small and the golden contract stable.

Speculative

Candidate C — Replace the CLI dispatch with a command registry

Files. cli.py.

Problem. main() is wide: eleven branches over string commands.

Solution. A registry of command objects with a uniform run(args) interface.

Benefits. Cleaner addition of future commands. Why not now. It would widen the module without deepening it, and it puts twelve exit-code contracts behind a new seam for no current caller. Rejected.

5. Top recommendation, restated

Tackle Candidate A first. It is the recently changed hot spot, it removes a leaked seam across three modules, and it gives Policy, Engine and ClaimVerifier one deep interface with real leverage. Candidate B returns when a second capture adapter exists. Candidate C stays out until width becomes the actual problem.
